A thread's log is a complete record of the run. `timeline()` reads it back in order, so you can debug a bad answer from production without adding logging first.

## Read a thread

Call `timeline()` on a run's thread. Later, with only the store and the thread id, open it with `openThread` / `open_thread`: you don't need the agent.

<Tabs items={["TypeScript", "Python"]} groupId="lang" persist>
<Tab value="TypeScript">

```ts
const thread = first.thread;

const timeline = await thread.timeline();
if (!timeline.ok) throw new Error(timeline.error.message);
for (const { event, fork_point } of timeline.value.entries) {
  console.log(event.seq, event.type, fork_point ? "(fork point)" : "");
}
```

</Tab>
<Tab value="Python">

```python
thread = first.thread

timeline = await thread.timeline()
if isinstance(timeline, Err):
    raise SystemExit(timeline.error.message)
for entry in timeline.value.entries:
    print(entry.event.seq, entry.event.type, "(fork point)" if entry.fork_point else "")
```

</Tab>
</Tabs>

`first` is the result of an earlier `agent.run`; its `thread` is the thread's handle in both languages.

Both return a value instead of throwing: check `ok` in TypeScript, or `isinstance(x, Err)` in Python (`from threads.result import Err`). A missing thread comes back as `not_found`.

<Callout>
The `sandbox` option is only needed if you want to [fork](/docs/evals/fork) or [save a case](/docs/evals/saved-cases) from this handle.
</Callout>

## What an entry looks like

Each entry is one recorded event plus a `fork_point` flag. An agent that wrote a file and then read it back produces a timeline like this:

```text
1 thread_started
2 user_input
3 model_request
4 model_response
5 tool_call
6 permission_decision
7 effect_begin
8 effect_commit
9 tool_result
10 model_request
11 model_response
12 turn_completed
13 snapshot (fork point)
14 user_input
...
```

Useful fields on `event`:

| Field | What it holds |
|---|---|
| `seq` | Position in the log, starting at 1 |
| `type` | What happened: `user_input`, `model_response`, `tool_call`, `tool_result`, `approval_requested`, `parked`, `turn_completed`, ... |
| `time` | When it was recorded (ms since epoch) |
| `actor` | Who caused it: the user, the model, the runtime, recovery |
| `data` | The event's payload, such as the tool name and input, or the result preview |

`thread_started` records the pinned setup: model, tools, instructions and permissions. `model_request` points to the exact request bytes the model received.

## Branches

A thread starts with one branch. Every [fork](/docs/evals/fork) adds another. `branches()` lists them:

<Tabs items={["TypeScript", "Python"]} groupId="lang" persist>
<Tab value="TypeScript">

```ts
const branches = await thread.branches();
console.log(branches);
```

</Tab>
<Tab value="Python">

```python
branches = await thread.branches()
print(branches)
```

</Tab>
</Tabs>

Each entry has `branch_id`, `runnable`, and for a fork its `parent_branch_id` and `fork_at_seq`. Open a specific branch with `openThread(store, id, { branchId })` / `open_thread(store, id, branch_id=...)`.

## From the command line

`threads timeline <thread_id>` prints the same timeline without writing code. See [CLI](/docs/production/cli).
