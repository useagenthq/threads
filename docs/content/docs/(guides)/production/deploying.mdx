A production host is the same module you ran with `threads dev`, started with `threads start`. There is no separate server to operate: the host is one process, and all of its state is in the store.

## Checklist

<Steps>
  <Step>
    ### Keep the store on a persistent disk

    `sqlite(".threads")` is a directory holding a SQLite database and stored artifacts. Everything lives there: every thread's log, the channel inbox, pending replies, schedule claims. Put it on a volume that survives redeploys, and back it up like any database.
  </Step>
  <Step>
    ### Provide secrets as environment variables

    Every `secret("NAME")` reads `NAME` from the host process environment: model keys (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`), sandbox keys (`E2B_API_KEY`, `DAYTONA_API_KEY`) and channel secrets. A missing channel secret stops startup with `missing_secret`.
  </Step>
  <Step>
    ### Protect the HTTP API

    Pass `authenticate` to `host()`. Without it the `/v1` API answers `401` to everyone, which is safe but not useful. Channel webhooks are verified with each provider's signing secret and don't need it. See [HTTP API](/docs/host/http-api).
  </Step>
  <Step>
    ### Start the host

    ```bash
    threads start
    ```
    See [CLI](/docs/production/cli) for the module each language loads and the port it listens on. Put it behind your usual HTTPS reverse proxy or load balancer and point each channel's webhook at `https://<your-domain>/channels/<name>/events`.
  </Step>
</Steps>

## Restarts and crashes

You can stop or restart the host at any time, including mid-run:

- Channel messages are stored before the provider gets its `200`, so nothing that was acknowledged is lost.
- On the next start the host picks up waiting messages, resumes runs and sends replies that are still owed.
- An action that may already have happened is never blindly retried. It is confirmed with the provider or held for a person. See [Durability & crash safety](/docs/production/durability).

## One machine or many

With the default SQLite store, run the host on one machine with the store on local disk. To run hosts on several processes or machines, or to fail over, use the Postgres store: every host points at the same database.

<Tabs items={["TypeScript", "Python"]} groupId="lang" persist>
<Tab value="TypeScript">

```ts
import { host } from "@threads/host";
import { postgres } from "@threads/postgres";

export default host({
  store: postgres(), // reads DATABASE_URL; or postgres("postgres://…")
  agents: { assistant },
  authenticate,
});
```

</Tab>
<Tab value="Python">

```python
from threads.host import host
from threads.postgres import postgres  # pip install "threads[postgres]"

app = host(store=postgres(), agents={"assistant": assistant}, authenticate=authenticate)
```

</Tab>
</Tabs>

Either way, each thread is owned by one process at a time: if a second process tries to run the same thread, it is refused rather than allowed to write alongside the first. Hosts sharing a store never double-fire a schedule.

On Postgres:

- It needs Postgres 16 or later. The first host to connect creates the tables in an empty database. A database of another store version is refused, as with SQLite; move threads between stores with `threads export` and `threads import`.
- Artifacts (spilled tool output, request bodies, snapshots) are stored in the database, so every machine can read them. `threads gc` removes the ones nothing refers to.
- `localMemory()` and `localKnowledge()` need a SQLite store. Use `supermemory()` or `zep()` instead.
- Keep the machines' clocks synchronized (NTP). Safety never depends on the clock, but a lease is taken over and gc's grace window is measured by it.
- The CLI's `--store` takes the database URL: `threads gc --store postgres://…`.

## Housekeeping

Two CLI commands keep a long-running store tidy. Neither runs automatically.

| Command | When |
|---|---|
| `threads gc [module]` | Periodically, for example from cron. Releases sandboxes that were left running and removes stored artifacts nothing refers to anymore. |
| `threads delete <thread_id>` / `threads delete --tenant <id>` | For retention or a customer's deletion request. |

## Containers and platforms

Any platform that runs a long-lived process with a persistent volume works: a VM, a container with a mounted volume, or a platform service with a disk. In Python you can also serve `app.asgi` with your own ASGI server; in TypeScript, mount `app.fetch` in your existing server (see [Host server](/docs/host/overview#mount-it-in-your-own-server)). Serverless functions without a persistent disk are not a good fit, because the store must outlive each request.
