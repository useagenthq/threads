An agent is a definition: a model, instructions and the tools it may use. Defining one does no I/O. Each `run()` starts a new thread (or continues one you pass), records every step to the log, and returns a result you can match on.

## Define and run

<Tabs items={["TypeScript", "Python"]} groupId="lang" persist>
<Tab value="TypeScript">

```ts
const support = agent({
  name: "support",
  instructions: "You answer billing questions. Be brief.",
  model: scriptedModel({ responses: [say("Your invoice is paid."), say("It was paid on 3 May.")] }),
});

const store = sqlite(":memory:");
const result = await support.run("Is my invoice paid?", { store });
```

</Tab>
<Tab value="Python">

```python
support = agent(
    name="support",
    instructions="You answer billing questions. Be brief.",
    model=scripted_model({"responses": [say("Your invoice is paid."), say("It was paid on 3 May.")]}),
)

store = sqlite(":memory:")
result = await support.run("Is my invoice paid?", store=store)
```

</Tab>
</Tabs>

`scriptedModel` plays back canned responses so these examples run with no API key. Swap in a real model from [Models](/docs/agents/models). Without `store`, runs use `sqlite(".threads")` in the working directory.

## Handle the result

A run never throws for an expected outcome. It returns one of six variants, keyed on `status`:

| `status` | What happened | What you get |
|---|---|---|
| `completed` | The agent finished its turn | `output`: the final text, or a typed value with [structured output](/docs/agents/structured-output) |
| `parked` | It is waiting on a person: an approval, a question, or a side effect whose outcome is unknown | `reason` and `pending` |
| `failed` | The turn ended with an error | `error.code`, `error.message` |
| `budget_exhausted` | A [budget](/docs/control/budgets) limit was hit | `budget` |
| `cancelled` | Someone cancelled the thread | |
| `handed_off` | The conversation moved to another agent ([handoffs](/docs/multi-agent/handoffs)) | `to_thread` |

Every variant carries `thread`, so you can continue, inspect or fork it.

<Tabs items={["TypeScript", "Python"]} groupId="lang" persist>
<Tab value="TypeScript">

```ts
function show(result: RunResult): string {
  switch (result.status) {
    case "completed":
      return result.output;
    case "parked":
      return `waiting: ${result.reason}`; // approval, question or an uncertain side effect
    case "failed":
      return `failed: ${result.error.code}`;
    case "budget_exhausted":
      return "out of budget";
    case "cancelled":
      return "cancelled";
    case "handed_off":
      return `continued in thread ${result.to_thread.id}`;
  }
}
```

</Tab>
<Tab value="Python">

```python
def show(result: RunResult[str]) -> str:
    match result:
        case Completed(output=output):
            return output
        case Parked(reason=reason):
            return f"waiting: {reason}"  # approval, question or an uncertain side effect
        case Failed(error=error):
            return f"failed: {error.code}"
        case BudgetExhausted():
            return "out of budget"
        case Cancelled():
            return "cancelled"
        case HandedOff(to_thread=to):
            return f"continued in thread {to.id}"
```

</Tab>
</Tabs>

A parked run is not lost. Answer it through the thread (see [Human-in-the-loop](/docs/control/human-in-the-loop)) and run again to continue.

## Continue a conversation

Pass the previous result's `thread` to keep going in the same conversation. The agent sees the full history.

<Tabs items={["TypeScript", "Python"]} groupId="lang" persist>
<Tab value="TypeScript">

```ts
const next = await support.run("When?", { thread: result.thread });
```

</Tab>
<Tab value="Python">

```python
next_result = await support.run("When?", thread=result.thread)
```

</Tab>
</Tabs>

In TypeScript `result.thread` is a small reference (`id`, `branch`, `store`); use [`openThread`](/docs/reference/functions/openThread) for the full handle. In Python it is already the full `Thread` handle.

## Change the reply style, or compact, between runs

An operator can steer a thread between runs without touching the agent's config. Both calls work only while the thread is idle; during a run they return `branch_busy`.

- `setOutputStyle` / `set_output_style` switches later replies to one of the styles you define with `outputStyles` / `output_styles`. The style is added to the conversation as an instruction, so the system prompt and the prompt cache stay as they are. The latest style applies; to go back, define a style for that too.
- `compact` asks the next run to summarize the conversation so far before it answers. Pass `instructions` to say what the summary must keep. The summary, or why it failed, shows up in the [timeline](/docs/evals/timeline).

<Tabs items={["TypeScript", "Python"]} groupId="lang" persist>
<Tab value="TypeScript">

```ts
const support = agent({
  model,
  outputStyles: { concise: "Answer in at most three sentences." },
});
const result = await support.run("Where is my invoice?", { store });

const operator = { issuer: "api", tenant: "local", subject: "operator" };
const opened = await openThread(store, result.thread.id);
if (!opened.ok) throw new Error(opened.error.message);
const thread = opened.value;

await thread.setOutputStyle("concise", operator);
await thread.compact(operator, { instructions: "Keep the open invoice numbers." });

// The next run summarizes first, then answers in the concise style.
await support.run("And the one from May?", { store, thread: result.thread });
```

</Tab>
<Tab value="Python">

```python
support = agent(
    model=model,
    output_styles={"concise": "Answer in at most three sentences."},
)
result = await support.run("Where is my invoice?", store=store)

from threads import Principal

operator = Principal(issuer="api", tenant="local", subject="operator")
await result.thread.set_output_style("concise", operator)
await result.thread.compact(operator, instructions="Keep the open invoice numbers.")

# The next run summarizes first, then answers in the concise style.
await support.run("And the one from May?", store=store, thread=result.thread)
```

</Tab>
</Tabs>

Styles are pinned with the agent's config: adding or changing one starts new threads, and a thread that was started with other styles refuses to continue with this config. An unknown style name is `not_found`, and the error lists the styles the thread knows.

## Stream a run

`stream()` runs the same loop and yields items as they happen: committed log events, plus live text deltas that are never stored. Await `result` for the final outcome.

<Tabs items={["TypeScript", "Python"]} groupId="lang" persist>
<Tab value="TypeScript">

```ts
const stream = streamed.stream("Hi", { store: sqlite(":memory:") });
for await (const item of stream) {
  if (item.kind === "delta") process.stdout.write(item.text); // live text, not stored
  else console.log(item.event.type); // a committed log event
}
const final = await stream.result;
```

</Tab>
<Tab value="Python">

```python
stream = streamed.stream("Hi", store=sqlite(":memory:"))
async for item in stream:
    if isinstance(item, DeltaItem):
        print(item.text, end="")  # live text, not stored
    elif isinstance(item, EventItem):
        print(item.event.type)  # a committed log event
final = await stream.result
```

</Tab>
</Tabs>

Python also yields a `StatusItem` while the run waits to retry a model call.

## Pass your own dependencies

Give tools access to your database, clients or config with `deps`. Deps stay in memory on your side: they are never written to the log or shown to the model. Tools read them from `ctx.deps`.

<Tabs items={["TypeScript", "Python"]} groupId="lang" persist>
<Tab value="TypeScript">

```ts
type Deps = { readonly db: Map<string, string> };

const lookupOrder = tool({
  name: "lookup_order",
  description: "Find an order's status by id.",
  input: z.object({ id: z.string() }),
  effect: "read_only",
  execute: async ({ id }, ctx: RunContext<Deps>) =>
    ctx.deps?.db.get(id) ?? "not found",
});

const shipped = await orders.run("Where is order 42?", {
  store: sqlite(":memory:"),
  deps: { db: new Map([["42", "shipped"]]) },
});
```

</Tab>
<Tab value="Python">

```python
@dataclass(frozen=True)
class Deps:
    db: dict[str, str]


class OrderInput(BaseModel):
    id: str


async def lookup(args: OrderInput, ctx: RunContext[Deps]) -> str:
    return ctx.deps.db.get(args.id, "not found")


shipped = await orders.run(
    "Where is order 42?",
    store=sqlite(":memory:"),
    deps=Deps(db={"42": "shipped"}),
)
```

</Tab>
</Tabs>

<Callout>
In Python, `deps=` is needed only when a tool reads it. When every tool takes `RunContext[None]`, leave it out and tools see `None`. For tools typed with your own deps class, pyright flags a run without `deps=`, and the run raises `ConfigError("invalid_config")`.
</Callout>

`ctx` also carries `thread_id`, `branch_id`, `principal` (who started the run) and, inside a tool, `call_id` and `effect_key`. See [RunContext](/docs/reference/types/RunContext).

## Options

All options are optional except `model`. Names are camelCase in TypeScript and snake_case in Python.

<Accordions type="multiple">
  <Accordion title="Model">
    - `model`: the model adapter. See [Models](/docs/agents/models).
    - `instructions`: the system prompt. It stays the same for the life of the thread.
    - `name`: shows in the log and is how other agents refer to this one. Default `"agent"`.
    - `retry`: retry policy for provider errors. See [Models](/docs/agents/models#retries).
    - `fallback`: backup models, tried in order. See [Fallback models](/docs/agents/models#fallback-models).
    - `output`, `outputRetries` (`output_retries`): typed final output. See [Structured output](/docs/agents/structured-output).
    - `context`: when to clear old tool output and compact long threads. Sensible defaults apply.
    - `outputStyles` (`output_styles`): named reply styles an operator can switch a thread to. See [Change the reply style](#change-the-reply-style-or-compact-between-runs).
  </Accordion>
  <Accordion title="Tools">
    - `tools`: your [tools](/docs/agents/tools) and [MCP servers](/docs/agents/mcp).
    - `extensions`: bundles of instructions, tools and [hooks](/docs/control/hooks).
    - `skills`: instructions the agent loads on demand. See [Skills](/docs/agents/skills).
    - `web`, `git`, `computer`, `lsp`: host-side [built-in tools](/docs/agents/built-in-tools).
  </Accordion>
  <Accordion title="Runtime">
    - `sandbox`: where shell and file tools run. See [Sandboxes](/docs/sandboxes/overview).
    - `egress`: sandbox network access. Absent means no internet.
  </Accordion>
  <Accordion title="Multi-agent">
    - `subagents`: agents this one may start. See [Subagents](/docs/multi-agent/subagents) and [Teams](/docs/multi-agent/teams).
    - `handoffs`: agents this one may hand the conversation to. See [Handoffs](/docs/multi-agent/handoffs).
  </Accordion>
  <Accordion title="Memory and knowledge">
    - `memory`, `memoryWrite`: long-term memory and who may write to it. See [Memory](/docs/memory/memory).
    - `knowledge`: a searchable knowledge base. See [Knowledge base](/docs/memory/knowledge).
  </Accordion>
  <Accordion title="Policy">
    - `permissions`: which tool calls run, ask or are denied. See [Permissions](/docs/control/permissions).
    - `approvers`: who may answer approvals. See [Human-in-the-loop](/docs/control/human-in-the-loop).
    - `budget`: limits on tokens, cost, turns and time. See [Budgets](/docs/control/budgets).
    - `onUnknownUsage` (`on_unknown_usage`): how budgets treat a model with no per-request bound. See [Budgets](/docs/control/budgets#cost-limits-need-a-price).
  </Accordion>
</Accordions>

## Run options

| Option | What it does |
|---|---|
| `thread` | Continue this thread instead of starting a new one |
| `store` | Where the log lives. Default `sqlite(".threads")` |
| `deps` | Your in-memory dependencies for tools and hooks |
| `budget` | A budget for this run |
| `principal` | Who is running it. Default: the local operator |
| `ceiling` | The strictest permissions this run and everything it starts may use |
| `signal` | An `AbortSignal` that stops the run in this process. TypeScript only |

To cancel a thread durably, from any process, use the thread's `cancel()`. See [Human-in-the-loop](/docs/control/human-in-the-loop).

## Check setup before running

`check()` reads your API keys, connects MCP servers and validates the whole setup without starting a thread. A problem comes back as a value that says what to set, and nothing stays connected afterwards.

<Tabs items={["TypeScript", "Python"]} groupId="lang" persist>
<Tab value="TypeScript">

```ts
const checked = await support.check();
if (!checked.ok) console.error(checked.error.message);
// anthropic: set apiKey or ANTHROPIC_API_KEY
```

</Tab>
<Tab value="Python">

```python
checked = await support.check()
if isinstance(checked, Err):
    print(checked.error.message)  # anthropic: set api_key or ANTHROPIC_API_KEY
```

</Tab>
</Tabs>

Fix the environment and call `check()` again on the same agent: it picks the change up. A run that hits the same problem throws it as `ConfigError` with a `code` before it records anything (a missing key, a duplicate tool name, a sandbox that can't enforce the egress you asked for, an unreachable MCP server). Everything that can go wrong during a run comes back as a result instead.
