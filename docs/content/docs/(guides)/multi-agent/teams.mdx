Give an agent a `team` and it becomes a lead. Its model can start members from the agents the team lists and send them messages. Each member runs in its own thread with its own model and tools. When a member finishes its task, the lead wakes up with the result and carries on, so `run()` returns the lead's answer after its members have reported.

Everything a team does is recorded in its logs: the lead's thread, one thread per member, and a team log. You can replay, fork and audit a team like any other thread.

## A complete example

The lead starts one researcher and answers. When the researcher is done, the lead wakes with its result and gives the final answer. Scripted models stand in for real ones, so this runs offline as a test.

<Tabs items={["TypeScript", "Python"]} groupId="lang" persist>
<Tab value="TypeScript">

```ts
import { agent, scriptedModel, sqlite } from "@threads/core";

const usage = { input_tokens: 10, output_tokens: 2 };
const say = (text: string) => ({
  content: [{ type: "text", text }],
  stop_reason: "end_turn",
  usage,
});
const start = (agentName: string, task: string) => ({
  content: [
    { type: "tool_use", call_id: "c1", name: "start", input: { agent: agentName, task } },
  ],
  stop_reason: "tool_use",
  usage,
});

const researcher = agent({
  name: "researcher",
  instructions: "Research the topic you are given. Answer in one sentence.",
  model: scriptedModel({ responses: [say("Battery pack prices fell this year.")] }),
});

const lead = agent({
  name: "lead",
  instructions: "Start a researcher on the topic, then report what it found.",
  model: scriptedModel({
    responses: [
      start("researcher", "Battery prices this year."),
      say("I started a researcher."),
      say("The researcher reports that battery pack prices fell this year."),
    ],
  }),
  team: [researcher],
});

const r = await lead.run("Report on battery prices.", { store: sqlite(":memory:") });
if (r.status === "completed") console.log(r.output);
// The team comes with every result, whatever the status.
console.log(`team ${r.team.ref.id}`);
```

```python
import asyncio

from pydantic import JsonValue

from threads import Completed, agent, scripted_model, sqlite

USAGE: JsonValue = {"input_tokens": 10, "output_tokens": 2}


def say(text: str) -> JsonValue:
    return {"content": [{"type": "text", "text": text}], "stop_reason": "end_turn", "usage": USAGE}


def start(agent_name: str, task: str) -> JsonValue:
    call: JsonValue = {"agent": agent_name, "task": task}
    return {
        "content": [{"type": "tool_use", "call_id": "c1", "name": "start", "input": call}],
        "stop_reason": "tool_use",
        "usage": USAGE,
    }


researcher = agent(
    name="researcher",
    instructions="Research the topic you are given. Answer in one sentence.",
    model=scripted_model({"responses": [say("Battery pack prices fell this year.")]}),
)

lead = agent(
    name="lead",
    instructions="Start a researcher on the topic, then report what it found.",
    model=scripted_model({
        "responses": [
            start("researcher", "Battery prices this year."),
            say("I started a researcher."),
            say("The researcher reports that battery pack prices fell this year."),
        ]
    }),
    team=[researcher],
)


async def main() -> None:
    r = await lead.run("Report on battery prices.", store=sqlite(":memory:"))
    if isinstance(r, Completed):
        print(r.output)
    # The team comes with every result, whatever the status.
    print(f"team {r.team.ref.id}")


asyncio.run(main())
```

It prints the lead's last answer, `The researcher reports that battery pack prices fell this year.` Its first answer, `I started a researcher.`, stays in the lead's timeline.

## The team tools

A lead and its members get these tools. Each call's result is a small JSON object the model reads.

| Tool | What it does | Result |
|---|---|---|
| `start` | Starts a member from an agent the team lists, with `task` as its first input. The member's name is `<agent>-<k>`, such as `researcher-1`, counting that agent's members in the team. Only the lead can start members. | `{"status": "started", "member": {...}}`, or `{"status": "refused", "code": ...}` |
| `send` | Sends `text` to a member by name. It arrives as the member's next input, and wakes the member if it is idle. Members can send to each other and to the lead. | `{"status": "sent", "id": ...}`, or `{"status": "refused", "code": ...}` |

A refusal is a value the model can act on, never an error that stops the run. `start` is refused with `unknown_agent` for an agent the team doesn't list, `concurrency_cap` when the team already has its limit of members running, `budget_exceeded` when a budget covering the new member has no room for one of its model requests, and `team_closed` once the lead has ended. `send` is refused with `unknown_member`, `member_ended`, `self` or `mailbox_full`.

A received message reaches the model as untrusted reference text, marked with its sender, never as an instruction.

## How a team runs

- **Members work in parallel.** Each member has its own thread and runs as soon as it starts. `run()` runs the members in the same process as the lead.
- **The lead wakes for each member it started.** When a member finishes its task, the lead gets its result as a message and takes another turn. `run()` returns once no lead turn is open and every member this run started has reported. The result is the lead's last answer.
- **A member that ends badly still reports.** If a member's model fails, it runs out of budget, or the next run no longer has its definition as it was when it started (the agent was renamed, dropped or changed), it ends `failed` (or `budget_exhausted`), and the lead wakes with that result instead.
- **A member that waits parks the lead.** If a member stops for an approval, the lead parks on it and `run()` returns `parked`, with the member in `pending`. Answer the approval on the member's thread (the lead's [timeline](/docs/evals/timeline) has the member's `member_started`, with its `thread_id`), then run the lead again: the member carries on, its result wakes the lead, and then your new input starts the next turn.
- **A lead that ends closes its team.** If the lead's own turn fails, is cancelled or runs out of budget, the run returns that status at once and the team is closed: no member can be started or resumed, and no message sent. A member already in the middle of a turn finishes that turn.
- **Budgets cover the whole team.** A member's model requests, and its own subagents', count against its own budget, the lead's budget, and the budget of the run its current work came from (the run that started it, or the run whose message it is answering). See [Budgets](/docs/control/budgets).
- **Safe after a crash.** Every step is one atomic append. If the process dies, the next run of the lead picks up where the logs left off: a member is started once, gets its task once, and reports once.

## Setting it up

```ts
const lead = agent({
  model,
  team: [researcher, writer],
  teamLimits: { concurrent: 4, mailbox: 100 },
});
```

- `team` lists the agents the lead may start. Passing it, even as `[]`, makes `agent()` return a `TeamAgent`, whose results carry `team`.
- The lead's instructions end with the names of the agents its team lists (`Agents you can start as team members with start: researcher, writer.`), so its model knows what `start` may name.
- `teamLimits.concurrent` caps how many members are starting or running at once (default 4). `teamLimits.mailbox` caps how many messages can wait for one member (default 100).
- An agent in a team can't hand off, so a listed agent with `handoffs` is refused when the lead is set up (`handoff_in_team`). A lead or member can't have its own tool named `start`, `send`, `ask`, `reply`, `wait`, `monitor` or `cancel` (`duplicate_name`). No agent in a team may be named `operator`, which marks text your own code writes (`invalid_config`).

<Callout>
  More team tools are on the way in this phase: `ask` and `reply`, `wait`, `monitor` and `cancel` for the model, and methods on the team handle (`team.start`, `team.send`, `team.ask`, `team.wait`, `team.members`) for your own code. Until they land, `r.team` names the team: `r.team.ref`.
</Callout>

## Specialists the lead defines

Sometimes the lead knows best what help it needs. A dynamic agent lets its model write a specialist's instructions, pick its tools and pick its model when it starts it, while your code still decides everything the specialist may ever have.

<Tabs items={["TypeScript", "Python"]} groupId="lang" persist>
<Tab value="TypeScript">

```ts
import { anthropic } from "@threads/anthropic";
import { agent, dynamicAgent, usd } from "@threads/core";

const specialist = dynamicAgent({
  name: "specialist",
  instructions: "You are a careful analyst. Cite the tool output you rely on.",
  tools: [readNotes, invoiceStatus], // the most a specialist can be given
  models: { fast: anthropic("claude-haiku-4-5"), strong: anthropic("claude-sonnet-5") },
  budget: { max_cost_nanos: usd(0.5) }, // every specialist's own cap
});

const lead = agent({
  name: "lead",
  instructions: "Split the question. Start a specialist for each part, with only the tools it needs.",
  model: anthropic("claude-sonnet-5"),
  team: [specialist],
});
```

</Tab>
<Tab value="Python">

```python
from threads import agent, dynamic_agent, usd
from threads.anthropic import anthropic

specialist = dynamic_agent(
    name="specialist",
    instructions="You are a careful analyst. Cite the tool output you rely on.",
    tools=[read_notes, invoice_status],  # the most a specialist can be given
    models={"fast": anthropic("claude-haiku-4-5"), "strong": anthropic("claude-sonnet-5")},
    budget={"max_cost_nanos": usd(0.5)},  # every specialist's own cap
)

lead = agent(
    name="lead",
    instructions="Split the question. Start a specialist for each part, with only the tools it needs.",
    model=anthropic("claude-sonnet-5"),
    team=[specialist],
)
```

</Tab>
</Tabs>

The lead's `start` call can then add up to four fields, all optional:

| Field | What the lead chooses | When it's left out |
|---|---|---|
| `instructions` | Text added after the specialist's own instructions, in a block marked as written by the lead | Only the specialist's own instructions |
| `tools` | Some of the specialist's tools, by name | All of them |
| `model` | One of the `models` keys | The first key |
| `label` | A display name for the timeline, such as `invoice checker`. It works on any start and is never shown to a model | No label |

Your code keeps the rest: permissions, approvals, hooks, skills, memory, the sandbox, the budget and the output schema all come from `dynamicAgent`, and the lead can't change them. A specialist given `tools: ["invoice_status"]` has exactly that tool, plus the team and bookkeeping tools every member keeps. It gets no shell and no web access, even when the template has a sandbox and web tools.

- **The lead sees its choices.** Its instructions list each dynamic agent with the tools and models it may choose, such as `specialist (you write its instructions; tools: invoice_status, read_notes; models: fast (default), strong)`.
- **A bad choice is refused, with the fix.** A tool or model the specialist doesn't have is refused `invalid_definition`, and the result lists what is allowed, so the model can try again. Written text that tries to close the block or copy the sentence after it is refused too.
- **Budgets use the chosen model.** `start` checks there's room for one request of the model the lead picked, so `strong` can be refused where `fast` would start.
- **It's all in the log.** The lead's `member_started` records what it chose (`define`) and the label, and the specialist's first event records the resulting instructions, tools and model. An approval raised by a specialist shows its name, label and `define`.
- **The written text is guidance, not a boundary.** It helps the specialist do the right job; the tools, permissions and budgets are what limit it.
- **Teams only.** A dynamic agent can't be a subagent or a handoff target, and it can't start members of its own.

## The subagent task board

Agents with `subagents` share a simpler task board: `team_task_create`, `team_task_claim`, `team_task_update` and `send_message`, recorded in the lead's log. It is separate from `team` and the two don't share anything. See [Subagents](/docs/multi-agent/subagents).
