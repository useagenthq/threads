A schedule starts a run of a host agent at each cron occurrence: a daily digest, a nightly cleanup, a weekly report.

<Tabs items={["TypeScript", "Python"]} groupId="lang" persist>
<Tab value="TypeScript">

```ts
const app = host({
  store: sqlite(".threads"),
  agents: { support },
  schedules: [
    {
      id: "daily_digest",
      agent: "support",
      cron: "0 9 * * 1-5",
      timezone: "Europe/Berlin",
      input: "Summarize yesterday's open tickets.",
    },
  ],
});
```

</Tab>
<Tab value="Python">

```python
from threads.host import Schedule, host

app = host(
    store=sqlite(".threads"),
    agents={"support": support},
    schedules=[
        Schedule(
            id="daily_digest",
            agent="support",
            cron="0 9 * * 1-5",
            timezone="Europe/Berlin",
            input="Summarize yesterday's open tickets.",
        ),
    ],
)
```

</Tab>
</Tabs>

Schedules start firing after `ready()`, which `threads dev` and `threads start` call for you.

## Fields

<Field name="id" type="string" required>
  A stable name for the schedule: lowercase letters, digits and underscores, starting with a letter. Keep it the same across deploys.
</Field>
<Field name="agent" type="string" required>
  A key of the host's `agents`.
</Field>
<Field name="cron" type="string" required>
  Five fields: minute, hour, day of month, month, day of week. Supports `*`, lists (`1,15`), ranges (`1-5`) and steps (`*/15`). Sunday is `0` or `7`.
</Field>
<Field name="timezone" type="string" default="UTC">
  An IANA time zone such as `America/New_York`.
</Field>
<Field name="input" type="string | InputPart[]" required>
  What each run starts with.
</Field>

## Guarantees

- **One run per occurrence.** Each occurrence is reserved in the store before it is decided, so two hosts on the same store, or a restart right at the boundary, never run it twice.
- **No catch-up storms.** Occurrences that fell due while the host was down are skipped as missed, not run late.
- **No pile-ups.** An occurrence that falls due while the schedule's previous run is still going is skipped as an overlap, even across a config change: a new thread starts only once the old one's run has finished.
- **Daylight saving.** A local time skipped by a spring-forward runs at the first valid minute after it; a time repeated by a fall-back runs once.
- A bad cron expression, an unknown time zone or an unknown agent fails `ready()` with a `ConfigError`.

## One thread per schedule config

A schedule keeps one thread, created at its first occurrence, for as long as its agent's config stays the same. Every occurrence is logged on it, so each config's history is one log you can read, replay and test:

- **Fired:** `schedule_fired`, then the run's input and the run itself.
- **Skipped:** `schedule_skipped` with a reason: `missed`, `overlap`, or `removed` (see below).

Each occurrence has the id `<schedule id>@<scheduled instant>`, for example `daily_digest@2026-09-23T07:00:00.000Z`, the same in both languages.

A thread keeps the agent config it started with, so changing the schedule's agent, or that agent's instructions, tools or model, starts a new thread at the next occurrence once the old thread's run has finished. The old thread stays in the store with its history, and a run left open on it is still resumed after a restart; its `schedule_fired` and `schedule_skipped` events name the schedule. Changing only the cron, time zone or input keeps the thread.

A due occurrence is reserved with the agent, input and time zone it fires with. So an occurrence reserved before you remove or change its schedule still fires as it was reserved. If its agent is no longer on the host, or its config changed since the thread started, it is logged as skipped with reason `removed`. Deleting a schedule's thread drops the occurrences it had reserved but not yet decided: they are never logged. The next occurrence starts a new thread.

Scheduled runs belong to the `local` tenant and are recorded with the schedule as the caller, so the [timeline](/docs/evals/timeline) shows which schedule started each run.
